# Repository Guidelines

## Project Structure & Module Organization

`default.nix` is the repository entry point. It imports pinned dependencies from `.tack/` and exposes NixOS, nix-darwin, WSL, and standalone Home Manager configurations. Machine definitions live under `hosts/`: `lemon/` is the desktop NixOS host, `wsl/` is the WSL system, and `darwin/` configures the Mac. User-specific Home Manager modules live in `home/<user>/`. Reusable editor modules belong in `modules/`, while static desktop images belong in `wallpapers/`.

Keep host-only settings in the relevant `hosts/<name>/` tree. Put shared behavior in `modules/`, and import it from user or host configuration rather than duplicating it.

## Build, Test, and Development Commands

- `nixfmt path/to/file.nix`: format each changed Nix file before committing.
- `nix eval -f ./default.nix nixosConfigurations.lemon.config.system.build.toplevel.drvPath`: evaluate Lemon without activating it; substitute another exported configuration as needed.
- `nh os switch`: rebuild Lemon using the configured `NH_FILE` and `NH_ATTRP` values.
- `nh os switch -f ./default.nix nixosConfigurations.wsl`: explicitly rebuild WSL.
- `nh home switch -f ./default.nix homeConfigurations.rick`: activate a user's Home Manager configuration.
- `tack look` and `tack update [input...]`: inspect or refresh pinned dependencies.

Do not introduce `flake.nix`; this repository intentionally uses Tack and `default.nix` while retaining the `flakes` evaluator feature for `fetchTree`.

## Coding Style & Naming Conventions

Use two-space indentation and standard `nixfmt` output. Prefer small modules with explicit imports and grouped option namespaces (for example, `programs`, `services`, and `environment`). Name host and user directories after their exported configuration keys. Avoid editing `.tack/default.nix`; it is generated by Tack. When changing pins, update both `.tack/pins.toml` and `.tack/pins.lock.json`.

## Testing Guidelines

There is no dedicated test suite. Treat successful formatting and evaluation of every affected configuration as the minimum check. For system-level changes, build or switch the target with `nh`; review activation output before considering the change complete. Never test a host change by switching an unrelated machine.

## Commit & Pull Request Guidelines

History favors short, lower-case, imperative subjects such as `add chaotic nyx` and `replace limine with systemd boot`. Keep each commit focused and use a specific subject; avoid vague messages like `do stuff`. Pull requests should identify affected hosts/users, summarize behavioral changes, list evaluation or rebuild commands run, and call out pin updates. Include screenshots only for visible desktop, editor, or wallpaper changes.
